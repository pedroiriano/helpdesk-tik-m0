## 2. Invariants Arsitektur & Keamanan M0 yang Mutlak Dipatuhi

1. **Satu Proses Go & Sembilan Schema PostgreSQL Terpisah**:
   - Tetap satu binary Go modular monolith dan satu instance PostgreSQL dengan sembilan database role/pool terisolasi (maksimal 4 koneksi per owner, total budget 36).
   - Dilarang membuat microservices baru, dilarang HTTP loopback palsu antar-modul, dan dilarang membuat *shared business service* atau *shared repository* yang mengaburkan batas domain.
2. **M3 Intake adalah Satu-satunya Penulis State Tiket**:
   - Modul M4 dan M5 dilarang menulis langsung ke tabel `m3.tickets` atau memanipulasi status tiket melalui query SQL internal mereka.
   - Perubahan status tiket (`OPEN` → `VERIFIED` → `DISPATCHED` / `ASSIGNED` atau `REJECTED`) wajib dieksekusi secara eksklusif oleh use case dan store privat M3.
   - Tidak boleh ada SQL JOIN lintas skema, *cross-schema foreign keys*, atau transaksi database lintas owner.
3. **Komunikasi Antar-Modul Melalui Public Port Tepercaya**:
   - Panggilan antar-modul bersifat in-process via interface port publik dengan parameter/return DTO (value semantics) dan konteks aktor tepercaya (`actor.Context`).
   - M5 memeriksa kelayakan teknisi (keanggotaan tim/unit kerja aktif) melalui port publik M1 `identity`.
   - M3 meminta rekomendasi klasifikasi atau mencatat keputusan klasifikasi melalui port publik M4 `classification`.
   - M3 mendelegasikan penugasan teknisi atau menerima hasil penugasan melalui port publik M5 `assignment`.
4. **Mutasi Atomik & Durable Outbox**:
   - Setiap mutasi status di M3 (verifikasi, penolakan, dispatch) wajib mengomit: data tiket, riwayat perubahan (`ticket_history`), log verifikasi, kuitansi idempotensi (bila ada), audit intent, dan pesan *transactional outbox* dalam **satu transaksi database lokal owner M3**.
   - Event `TicketVerified` dan `TicketDispatched` wajib diterbitkan ke outbox M3 dan dikonsumsi oleh M9 melalui pola outbox/inbox durable dengan ACK eksplisit.

## 3. Urutan Kerja & Hasil Wajib (Step-by-Step Implementation)

### Langkah 1: Penyelarasan Kontrak, DTO, Event, dan Migrasi DDL (Contract-First)
1. **Perluasan OpenAPI Bisnis (`contracts/openapi/business.json`)**:
   - Definisikan operasi verifikasi tiket di M3:
     - `POST /api/v1/tickets/{id}/verify` (operator menyetujui tiket masuk, memperbarui urgensi/kategori final, status menjadi `VERIFIED`).
     - `POST /api/v1/tickets/{id}/reject` (operator menolak tiket dengan alasan wajib, status menjadi `REJECTED`).
   - Definisikan operasi klasifikasi di M4:
     - Endpoint atau internal port untuk evaluasi rekomendasi: kategori, sub-kategori, urgensi awal, tingkat dampak, dan confidence score.
     - Struktur pencatatan override: jika operator mengganti rekomendasi sistem, wajib mengirim `override_reason` / `justification` (alasan perubahan).
   - Definisikan operasi dispatch dan penugasan di M5:
     - `POST /api/v1/tickets/{id}/dispatch` atau `POST /api/v1/tickets/{id}/assign`:
       - Parameter wajib: `expected_version` (integer untuk CAS optimistic locking), `technician_id`, `tier` (`L1` atau `L2`), serta instruksi penugasan awal.
   - Definisikan antrean kerja operator & teknisi:
     - `GET /api/v1/operator/queue/verification` (daftar tiket berstatus `OPEN` menunggu verifikasi).
     - `GET /api/v1/operator/queue/dispatch` (daftar tiket berstatus `VERIFIED` menunggu penugasan teknisi).
     - `GET /api/v1/technician/queue/my-tasks` (daftar tiket yang ditugaskan ke teknisi login aktif).
2. **DDL Migrasi Additive Per Owner**:
   - Rancang migrasi SQL baru bernomor monoton (misal `018-m3-verification.sql`, `019-m4-classification.sql`, `020-m5-assignment.sql` atau format standar repositori):
     - **M3 (`m3_intake`)**: Kolom/tabel untuk timestamp verifikasi, verifier ID, rejection reason, assigned technician ref (snapshot), assignment tier (`L1`/`L2`), dan version lock counter.
     - **M4 (`m4_classification`)**: Tabel log rekomendasi sistem, confidence level, input features, final decision, flag `is_overridden`, dan teks `override_reason`.
     - **M5 (`m5_assignment`)**: Tabel assignment tiket, riwayat disposisi, status penugasan teknisi (`ASSIGNED`, `ACCEPTED`, `TRANSFERRED`), level teknisi (`L1`/`L2`), serta tracking beban kerja teknisi aktif.
   - Daftarkan migrasi pada `migrations/manifest.json` lengkap dengan sha256 checksum dan owner ID.
   - **Gate Database Disposable**: Uji coba penerapan migrasi pada PostgreSQL disposable terisolasi, validasi hak akses per-role (M3, M4, M5 dilarang akses tabel sibling), dan uji idempotensi penerapan ulang sebelum menyentuh DB kerja lokal.
   - Perbarui readiness health check di Go backend bila terdapat kenaikan versi marker skema domain.

### Langkah 2: Verifikasi Tiket & State Machine Guard pada M3 (AC04)
1. **Aturan Invariant Status (Strict State Guard)**:
   - Tiket yang baru masuk berstatus `OPEN` (belum diverifikasi).
   - **Guard Penolakan Dispatch**: Tiket yang masih berstatus `OPEN` dilarang keras langsung di-dispatch ke teknisi. Percobaan dispatch tiket `OPEN` wajib ditolak dengan respons **`409 Conflict`** atau **`422 Unprocessable Content`** dengan error code eksplisit `TICKET_NOT_VERIFIED`.
   - Tiket hanya boleh di-dispatch apabila telah melewati proses verifikasi dan statusnya telah berubah menjadi **`VERIFIED`**.
2. **Hak Akses & Otorisasi Operator**:
   - Aksi verifikasi dan penolakan hanya dapat dieksekusi oleh pengguna dengan peran/izin operator yang sah (misal `ticket:verify` / peran `OPERATOR` / `HELPDESK_STAFF`).
   - Akses dari pengguna publik, tamu (guest capability), atau admin konfigurasi tanpa hak operator wajib ditolak dengan **`403 Forbidden`** (atau `401 Unauthorized` jika unauthenticated).
3. **Eksekusi Verifikasi & Penolakan**:
   - Jika diverifikasi: status tiket menjadi `VERIFIED`, rekam waktu verifikasi dan identitas operator, naikkan versi tiket (`version = version + 1`), rekam riwayat verifikasi di `ticket_history`, dan terbitkan event `TicketVerified` ke outbox M3.
   - Jika ditolak: operator wajib menyertakan alasan penolakan (`rejection_reason`). Status tiket menjadi `REJECTED`, rekam audit, dan terbitkan event `TicketRejected`. Penolakan tanpa alasan wajib ditolak dengan **`400 Bad Request`**.

### Langkah 3: Engine Rekomendasi Klasifikasi M4 & Operator Override (AC13)
1. **Engine Rekomendasi M4**:
   - Sediakan logika domain penentuan kategori dan urgensi di M4 berbasis aturan deterministik (*rule-based domain engine*) berdasarkan: metadata layanan M2, kata kunci kendala, dampak pada layanan publik/ASN, dan lokasi/perangkat.
   - Hasilkan rekomendasi terstruktur: `suggested_category_id`, `suggested_urgency` (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`), dan `confidence_score` (0.00–1.00).
2. **Pencatatan Keputusan & Override Operator**:
   - Operator saat melakukan verifikasi dapat:
     a. **Menerima Rekomendasi**: Nilai rekomendasi M4 disahkan menjadi klasifikasi tiket di M3.
     b. **Melakukan Override**: Operator memilih kategori atau urgensi yang berbeda dari rekomendasi M4.
   - **Invariant Override**: Setiap override operator **wajib menyertakan teks catatan/alasan override** (`override_reason`, minimal batas karakter yang masuk akal, misal 5–500 karakter).
   - Upaya override tanpa menyertakan alasan wajib digagalkan oleh server dengan **`400 Bad Request`** (`OVERRIDE_REASON_REQUIRED`).
   - M4 mencatat riwayat rekomendasi vs keputusan final dan alasan override secara persisten dan dapat diaudit.

### Langkah 4: Routing Disposisi L1/L2 & Optimistic Concurrency CAS pada M5 (AC13)
1. **Penugasan Teknisi Berjenjang (L1 vs L2)**:
   - Dukung penugasan ke dua tingkatan teknisi:
     - **Level 1 (L1)**: Dukungan teknis penanganan awal / insiden umum (perangkat kerja, printer, instalasi aplikasi standar, reset akun dasar).
     - **Level 2 (L2)**: Penanganan lanjutan / spesialis infrastruktur (jaringan backbone, server, keamanan siber, integrasi database).
   - Validasi Teknisi: M5 memvalidasi bahwa `technician_id` yang dipilih adalah personil yang valid, aktif, dan memiliki kompetensi/keanggotaan unit kerja yang sesuai melalui public port M1 `identity`. Penugasan ke akun non-staf atau user nonaktif wajib ditolak dengan **`422 Unprocessable Content`**.
2. **Pengamanan Konkurensi Optimistik (Compare-And-Swap / CAS Version Guard)**:
   - Untuk mencegah insiden *conflicting dispatch* atau *double-assignment* ketika dua operator membuka tiket yang sama secara bersamaan:
     - Payload dispatch wajib menyertakan atribut **`expected_version`** (versi tiket yang sedang dibaca oleh klien).
     - Saat commit di M3, query update state tiket wajib menggunakan klausa penjaga versi:
       `UPDATE m3.tickets SET status = 'DISPATCHED', version = version + 1, ... WHERE id = $1 AND version = $2`
     - **Penanganan Konflik**:
       - Operator A (mengirim versi `N` lebih dulu) berhasil memperbarui tiket menjadi versi `N + 1`.
       - Operator B (mengirim request beberapa saat kemudian dengan versi `N` yang kini sudah usang) **wajib menerima respons `409 Conflict`** dengan detail pesan bahwa tiket telah diperbarui oleh operator lain. Data tiket tidak boleh tertimpa diam-diam!
3. **Pencatatan Tugas & Outbox Event**:
   - M5 mencatat record penugasan di skema `m5`, mencatat timestamp penugasan, instruksi kerja, dan mengaitkan status penugasan.
   - Terbitkan outbox event `TicketDispatched` / `TicketAssigned` yang memuat referensi ID tiket, teknisi penerima tugas, tingkat tier (L1/L2), dan versi tiket.

### Langkah 5: Integrasi Antarmuka Petugas PIUI Zero (Admin Workspace UI)

## 4. Kriteria Pengujian Penerimaan & Bukti Wajib (Evidence Plan)

Implementasi M0-05 hanya dapat dinyatakan selesai apabila didukung oleh pengujian positif dan negatif riil pada Go, PostgreSQL, dan Browser:

1. **Pengujian AC04 (Verifikasi Intake & Guard Status)**:
   - **Uji Positif**: Tiket `OPEN` diverifikasi oleh operator sah → status berubah menjadi `VERIFIED`, `version` bertambah 1, `ticket_history` terekam, event `TicketVerified` masuk outbox.
   - **Uji Negatif (Dispatch Tanpa Verifikasi)**: Percobaan mendispatch tiket yang masih berstatus `OPEN` wajib ditolak (respons 409 Conflict atau 422 Unprocessable).
   - **Uji Negatif (Otorisasi)**: Request verifikasi dari sesi tamu publik (guest capability) atau ASN pemohon ditolak dengan 403 Forbidden.
   - **Uji Negatif (Penolakan Tanpa Alasan)**: Menolak tiket tanpa menyertakan `rejection_reason` wajib ditolak dengan 400 Bad Request.
2. **Pengujian AC13 (Klasifikasi, Override, Routing L1/L2 & CAS)**:
   - **Uji Rekomendasi M4**: Verifikasi bahwa engine M4 menghasilkan rekomendasi kategori dan urgensi yang konsisten untuk data uji sintetis.
   - **Uji Override M4**: Operator melakukan override dengan menyertakan alasan → tersimpan sukses dan terekam di audit. Override tanpa alasan → ditolak 400 Bad Request.
   - **Uji Routing L1/L2 M5**: Tiket dapat dialokasikan ke teknisi L1 atau L2 yang sah; penugasan ke user non-staf ditolak 422.
   - **Uji Konkurensi Optimistik (CAS)**:
     - Simulasikan 2 request dispatch serentak terhadap tiket yang sama dengan `expected_version` yang identik.
     - Buktikan bahwa tepat **1 request berhasil** (status berubah menjadi `DISPATCHED`, versi naik) dan **1 request kedua gagal dengan 409 Conflict**.
     - Buktikan tidak terjadi korupsi data, tidak ada data ganda di M5, dan state di database konsisten.
3. **Pemeriksaan Batas & Regresi Arsitektur**:
   - Jalankan `python scripts/check_boundaries.py` → wajib **PASS** (tidak ada impor ilegal antar package).
   - Jalankan `go test ./...` dari folder `backend` → seluruh test suite lama (M0-01 s/d M0-04) dan test suite baru M0-05 wajib **100% PASS**.
   - Jalankan `python scripts/test_piui_build.py` dan periksa ketiadaan error build frontend.
4. **Verifikasi Browser Representatif (Headless Chrome)**:
   - Uji alur antarmuka admin PIUI Zero: login sebagai operator lab → buka antrean verifikasi → verifikasi tiket dengan override alasan → buka antrean disposisi → lakukan dispatch ke teknisi L1 → konfirmasi perubahan tiket di UI.
   - Uji penolakan UI saat terjadi error 409 Conflict.
   - Uji navigasi keyboard (fokus input, aktivasi tombol, modal escape) dan keselarasan viewport mobile (`390x844`) serta desktop (`1440x900`).
5. **Pencatatan Bukti Faktual (Evidence Ledger)**:

## 5. Batasan Operasional & Larangan Keras (Definition of Stop)

1. **Jangan Melakukan Tindakan Destruktif**:
   - Dilarang mereset, men-drop, atau men-truncate database kerja PostgreSQL lokal.
   - Dilarang merotasi secret lokal di `.local/secrets`.
   - Dilarang mengutak-atik kontainer atau volume Docker lain di luar project `helpdesk-m0`.
2. **Jangan Mengubah Berkas Rujukan Kanonis**:
   - Dilarang memodifikasi berkas di dalam direktori `references/` (seperti `references/piui-modern` atau `references/piui-zero`) demi kelulusan tes; segala adaptasi hanya dilakukan pada layer template builder di `frontend/`.
3. **Jangan Membuat Klaim Palsu**:
   - Dilarang memalsukan exit code, dilarang mengklaim tes lulus tanpa menjalankan command riil, dan dilarang menganggap perencanaan sebagai bukti pengujian.
   - Jika fitur scheduler SLA 24 jam atau eskalasi belum dibangun, akui secara jujur sebagai `NOT_IMPLEMENTED` (fase M0-06).
4. **Batas Berhenti (Stop Boundary)**:
   - **Berhenti setelah M0-05 selesai dan terbukti tuntas**.
   - **Dilarang otomatis memulai M0-06** (SLA, resolusi, scheduler 24 jam), M0-07, atau eksperimen komparasi model riset (C3/F9/G-OPT). Tunggu instruksi eksplisit pengguna untuk fase berikutnya.

Tuntaskan fase ini secara mandiri, presisi, bersih dari error, dan laporkan hasilnya secara ringkas berbasis bukti nyata!
